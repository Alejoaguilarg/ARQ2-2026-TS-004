## 1. Overview

Finova replaces the chained synchronous call `User-Service -> Wallet-Service -> Notification-Service` with an API Gateway in front of five services that coordinate money movement through an orchestrated saga over RabbitMQ. Each service is hexagonal and owns its PostgreSQL database.

| Service | Bounded context | Responsibility | Datastore | Publishes | Consumes |
|---|---|---|---|---|---|
| **API Gateway** (Spring Cloud Gateway) | Edge (infrastructure) | Single entry point. JWT validation (JWKS), revocation check, financial-session enforcement, mandatory `Idempotency-Key` pre-check, rate limiting and lockout, routing, `X-Correlation-Id` injection. | Redis | `audit.events` (rejected and duplicate attempts) | — |
| **Identity Service** | Identity | Users, credentials, devices, login, access token (15 min) and rotating refresh token (7 days), financial session (step-up with PIN or OTP), revocation. | `identity_db` + Redis | — | — |
| **Transfer Service** | Transfer (core) | Transfer aggregate and state machine, saga orchestration (debit, credit, complete or compensate), idempotency defense in depth, transactional outbox. | `transfer_db` | `wallet.commands`, `transfer.events`, `audit.events` | `wallet.events` |
| **Wallet Service** | Wallet | Wallet aggregate, non-negative balance invariant, conditional atomic debit, credit, reversal, ledger entries, balance read model in Redis (CQRS). | `wallet_db` + Redis | `wallet.events`, `audit.events` | `wallet.commands` |
| **Audit Service** | Audit | Append-only, hash-chained record of every attempt and outcome. Read API for compliance. | `audit_db` | — | `audit.events` |
| **Notification Service** | Notification | Push, email and SMS from outcome events. Best effort, never on the critical path. | `notification_db` | — | `transfer.events` |

End-to-end transfer flow:

```
App --POST /transfers (Idempotency-Key, X-Financial-Session)--> Gateway
Gateway: JWT ok -> financial session ok -> SET NX idem key -> route
Transfer Service: INSERT transfer(PENDING) + outbox(DebitWallet) in ONE tx -> 202 Accepted
Outbox relay -> wallet.commands: DebitWallet
Wallet: conditional debit (balance >= amount) -> WalletDebited | DebitRejected
Transfer: DEBITED -> CreditWallet
Wallet: credit -> WalletCredited | CreditFailed
Transfer: COMPLETED  (or COMPENSATING -> ReverseDebit -> DebitReversed -> REVERSED)
transfer.events -> Notification ; audit.events -> Audit
```

## 2. Conventions

- **Base URL:** `https://api.finova.local/api/v1` (all traffic enters through the Gateway on port 8080).
- **Format:** JSON, UTF-8. Timestamps are ISO-8601 UTC. Identifiers are UUID v4.
- **Money:** `amount` is a decimal string with 2 decimals (`"150000.00"`) and `currency` is ISO-4217 (`COP`). Never a float. Stored as `NUMERIC(19,2)`.
- **Authentication:** `Authorization: Bearer <accessToken>` (JWT, RS256, 15 min). Claims: `sub` (userId), `deviceId`, `roles`, `jti`, `exp`.
- **Financial session:** `X-Financial-Session: <financialSessionToken>` (JWT, 5 min, single use, scope `transfer:create`, bound to `sub` and `deviceId`).
- **Idempotency:** `Idempotency-Key: <uuid>` is **mandatory** on `POST /transfers`. The client generates one key per transfer intent and reuses it on every retry.
- **Tracing:** `X-Correlation-Id` is accepted or generated by the Gateway and propagated in every HTTP call, message header and log line, together with `transferId`.
- **Errors:** `application/problem+json` (RFC 9457).

```json
{
  "type": "https://finova.local/problems/insufficient-funds",
  "title": "Insufficient funds",
  "status": 422,
  "code": "INSUFFICIENT_FUNDS",
  "detail": "Available balance is lower than the requested amount.",
  "correlationId": "5f0c7a52-3b0e-4d3a-9d6e-0c4f8b1d2e11",
  "timestamp": "2026-10-16T15:04:05Z"
}
```

Common error codes: `UNAUTHENTICATED` (401), `TOKEN_REVOKED` (401), `FORBIDDEN` (403), `FINANCIAL_SESSION_REQUIRED` (403), `FINANCIAL_SESSION_INVALID` (403), `VALIDATION_ERROR` (400), `IDEMPOTENCY_KEY_REQUIRED` (400), `IDEMPOTENCY_IN_PROGRESS` (409), `IDEMPOTENCY_KEY_REUSED` (422), `INSUFFICIENT_FUNDS` (422), `ACCOUNT_LOCKED` (423), `RATE_LIMITED` (429), `INTERNAL_ERROR` (500), `SERVICE_UNAVAILABLE` (503).

## 3. Domain data schemas

### 3.1 Identity context (`identity_db`)

| Entity | Fields |
|---|---|
| `User` | `userId` UUID PK, `email` unique, `phone`, `passwordHash` (argon2id), `pinHash` (argon2id), `status` (`ACTIVE`, `LOCKED`, `DISABLED`), `failedAttempts` int, `lockedUntil` timestamp, `createdAt` |
| `Device` | `deviceId` UUID PK, `userId` FK, `fingerprint`, `trusted` bool, `lastSeenAt` |
| `Session` | `sessionId` UUID PK, `userId`, `deviceId`, `refreshTokenHash`, `familyId` (rotation chain), `expiresAt`, `revokedAt` |
| `FinancialSession` | `financialSessionId` (= token `jti`), `userId`, `deviceId`, `method` (`PIN`, `OTP`), `scope` (`transfer:create`), `expiresAt`, `usedAt` |

Redis keys: `revoked:jti:{jti}` (TTL = remaining token life), `fs:used:{jti}` (TTL 5 min), `ratelimit:{userId|ip}:{window}`, `login:fail:{userId}`.

### 3.2 Wallet context (`wallet_db`)

| Entity | Fields | Invariants |
|---|---|---|
| `Wallet` | `walletId` UUID PK, `userId` unique, `currency`, `balance` NUMERIC(19,2), `version` bigint, `status` (`ACTIVE`, `BLOCKED`), `updatedAt` | `balance >= 0` (CHECK constraint and conditional update); `version` increases by 1 on every change |
| `LedgerEntry` | `entryId` UUID PK, `walletId`, `transferId`, `type` (`DEBIT`, `CREDIT`, `REVERSAL`), `amount`, `balanceAfter`, `createdAt` | Append-only. `UNIQUE(transferId, type)` makes every operation idempotent |
| `OutboxMessage` | `messageId` UUID PK, `aggregateId`, `exchange`, `routingKey`, `payload` JSONB, `headers` JSONB, `createdAt`, `publishedAt` | Written in the same transaction as the state change |
| `ProcessedMessage` | `messageId` PK, `processedAt` | Consumer deduplication |

Conditional debit (single statement, no overdraft under concurrency):

```sql
UPDATE wallets
   SET balance = balance - :amount, version = version + 1, updated_at = now()
 WHERE wallet_id = :walletId AND status = 'ACTIVE' AND balance >= :amount
RETURNING balance, version;   -- 0 rows => DebitRejected(INSUFFICIENT_FUNDS)
```

Balance read model in Redis: hash `balance:{userId}` = `{walletId, available, currency, version, updatedAt}`. Updated only if `incoming.version > stored.version` (Lua script compare-and-set).

### 3.3 Transfer context (`transfer_db`)

| Entity | Fields |
|---|---|
| `Transfer` | `transferId` UUID PK, `idempotencyKey`, `requestHash` (SHA-256 of canonical body), `senderUserId`, `senderWalletId`, `receiverWalletId`, `amount`, `currency`, `description`, `status`, `failureReason`, `attempts`, `version`, `createdAt`, `updatedAt`. `UNIQUE(sender_user_id, idempotency_key)` |
| `SagaStep` | `transferId`, `step` (`DEBIT`, `CREDIT`, `REVERSE`), `status` (`SENT`, `SUCCEEDED`, `FAILED`), `attempt`, `deadline`, `updatedAt` |
| `OutboxMessage`, `ProcessedMessage` | Same as in Wallet |

Transfer state machine:

```
PENDING --WalletDebited--> DEBITED --WalletCredited--> COMPLETED
PENDING --DebitRejected--> REJECTED
DEBITED --CreditFailed | credit timeout after 3 retries--> COMPENSATING --DebitReversed--> REVERSED
```

`COMPLETED`, `REJECTED` and `REVERSED` are terminal. Any other transition is refused by the aggregate.

### 3.4 Audit context (`audit_db`)

| Entity | Fields |
|---|---|
| `AuditRecord` | `seq` BIGSERIAL PK, `eventId` UUID unique, `transferId`, `userId`, `source` (`GATEWAY`, `TRANSFER`, `WALLET`), `action`, `outcome`, `amount`, `currency`, `reason`, `correlationId`, `occurredAt`, `recordedAt`, `prevHash`, `hash` |

`hash = SHA-256(prevHash || canonicalJson(record))`. The service role only has `INSERT` and `SELECT`; `UPDATE`, `DELETE` and `TRUNCATE` are revoked and a trigger rejects them.

### 3.5 Notification context (`notification_db`)

`NotificationLog`: `notificationId`, `transferId`, `userId`, `channel` (`PUSH`, `EMAIL`, `SMS`), `template`, `status` (`SENT`, `FAILED`), `attempts`, `createdAt`. Plus `ProcessedMessage`.

## 4. REST APIs

All endpoints are exposed by the Gateway. `Auth` lists what the Gateway enforces before routing.

### 4.1 Identity Service

#### `POST /auth/register`
- **Auth:** none (rate limited per IP).
- **Request:** `{ "email": "ana@mail.com", "phone": "+573001112233", "password": "S3cure!pass", "pin": "4826" }`
- **Responses:** `201 Created` `{ "userId": "…", "walletId": "…" }` · `400 VALIDATION_ERROR` · `409 EMAIL_ALREADY_REGISTERED` · `429 RATE_LIMITED` · `500 INTERNAL_ERROR`

#### `POST /auth/login`
- **Auth:** none. Lockout after 5 failed attempts in 15 minutes.
- **Request:** `{ "email": "ana@mail.com", "password": "S3cure!pass", "deviceId": "8c1e…" }`
- **Responses:**
  - `200 OK`
    ```json
    { "accessToken": "eyJ…", "expiresIn": 900, "refreshToken": "rt_…", "refreshExpiresIn": 604800, "tokenType": "Bearer" }
    ```
  - `401 UNAUTHENTICATED` · `423 ACCOUNT_LOCKED` · `429 RATE_LIMITED` · `500 INTERNAL_ERROR`

#### `POST /auth/refresh`
- **Auth:** refresh token in body. Rotation: each refresh token is single use; reusing an old one revokes the whole family.
- **Request:** `{ "refreshToken": "rt_…", "deviceId": "8c1e…" }`
- **Responses:** `200 OK` (same body as login) · `401 TOKEN_REVOKED` · `500 INTERNAL_ERROR`

#### `POST /auth/logout`
- **Auth:** Bearer.
- **Effect:** revokes the session and adds the access token `jti` to `revoked:jti:*` in Redis.
- **Responses:** `204 No Content` · `401 UNAUTHENTICATED`

#### `POST /auth/financial-session`
- **Auth:** Bearer. Step-up for money movement (Feature 1).
- **Request:** `{ "method": "PIN", "pin": "4826" }` or `{ "method": "OTP", "otp": "123456" }`
- **Responses:**
  - `201 Created`
    ```json
    { "financialSessionToken": "eyJ…", "scope": "transfer:create", "expiresIn": 300 }
    ```
  - `401 UNAUTHENTICATED` · `403 STEP_UP_FAILED` · `423 ACCOUNT_LOCKED` (3 failed PIN attempts) · `500 INTERNAL_ERROR`

#### `GET /.well-known/jwks.json`
- **Auth:** none. Public keys the Gateway uses to validate tokens locally. `200 OK`.

### 4.2 Wallet Service

#### `GET /wallets/me/balance`
- **Auth:** Bearer. Rate limit 50 req/s per user.
- **Read path (Feature 2):** Redis `balance:{userId}`; on miss, read PostgreSQL and warm the cache.
- **Responses:**
  - `200 OK`
    ```json
    { "walletId": "b7d2…", "available": "850000.00", "currency": "COP", "version": 42, "asOf": "2026-10-16T15:04:05.120Z" }
    ```
  - `401 UNAUTHENTICATED` · `404 WALLET_NOT_FOUND` · `429 RATE_LIMITED` · `503 SERVICE_UNAVAILABLE`
- **Target:** p99 < 50 ms at 2,000 req/s on the local Docker Compose setup.

#### `GET /wallets/me/ledger?page=0&size=20`
- **Auth:** Bearer.
- **Responses:** `200 OK` `{ "items": [ { "entryId": "…", "transferId": "…", "type": "DEBIT", "amount": "150000.00", "balanceAfter": "850000.00", "createdAt": "…" } ], "page": 0, "size": 20, "total": 37 }` · `401` · `500`

### 4.3 Transfer Service

#### `POST /transfers`
- **Auth:** Bearer + `X-Financial-Session` + `Idempotency-Key` (all mandatory).
- **Request:**
  ```json
  { "receiverWalletId": "e41a…", "amount": "150000.00", "currency": "COP", "description": "Rent share" }
  ```
- **Gateway idempotency (Feature 3):**
  1. Missing key → `400 IDEMPOTENCY_KEY_REQUIRED`.
  2. `SET idem:{userId}:{key} {status:IN_PROGRESS, requestHash} NX EX 86400`.
  3. Key exists, `IN_PROGRESS` → `409 IDEMPOTENCY_IN_PROGRESS` (header `Retry-After: 1`, body includes `transferId` when known).
  4. Key exists, `COMPLETED`, same `requestHash` → stored response replayed with header `Idempotent-Replayed: true`. Nothing is executed.
  5. Key exists, different `requestHash` → `422 IDEMPOTENCY_KEY_REUSED`.
- **Responses:**
  - `202 Accepted` (header `Location: /api/v1/transfers/{transferId}`)
    ```json
    { "transferId": "a3f9…", "status": "PENDING", "statusUrl": "/api/v1/transfers/a3f9…" }
    ```
  - `400 VALIDATION_ERROR | IDEMPOTENCY_KEY_REQUIRED` · `401 UNAUTHENTICATED` · `403 FINANCIAL_SESSION_REQUIRED | FINANCIAL_SESSION_INVALID` · `409 IDEMPOTENCY_IN_PROGRESS` · `422 IDEMPOTENCY_KEY_REUSED | SAME_WALLET` · `429 RATE_LIMITED` · `503 SERVICE_UNAVAILABLE`
- Insufficient funds is not a synchronous error: the transfer ends in `REJECTED` with `failureReason: INSUFFICIENT_FUNDS` (the authoritative check happens atomically in Wallet).

#### `GET /transfers/{transferId}`
- **Auth:** Bearer (only sender or receiver).
- **Responses:**
  - `200 OK`
    ```json
    { "transferId": "a3f9…", "status": "COMPLETED", "amount": "150000.00", "currency": "COP",
      "senderWalletId": "b7d2…", "receiverWalletId": "e41a…", "failureReason": null,
      "createdAt": "2026-10-16T15:04:05Z", "updatedAt": "2026-10-16T15:04:05.480Z" }
    ```
  - `401` · `403 FORBIDDEN` · `404 TRANSFER_NOT_FOUND`

### 4.4 Audit Service

#### `GET /audit/records?transferId=&userId=&from=&to=&page=&size=`
- **Auth:** Bearer with role `AUDITOR` (Admin Dashboard).
- **Responses:** `200 OK` `{ "items": [ { "seq": 1042, "eventId": "…", "transferId": "a3f9…", "source": "GATEWAY", "action": "TRANSFER_REQUESTED", "outcome": "DUPLICATE_REPLAYED", "occurredAt": "…", "hash": "9b1f…" } ], "page": 0, "total": 11 }` · `401` · `403 FORBIDDEN` · `500`

#### `GET /audit/verify?from=&to=`
- **Auth:** role `AUDITOR`. Recomputes the hash chain.
- **Responses:** `200 OK` `{ "valid": true, "checked": 15000 }` or `{ "valid": false, "brokenAtSeq": 1042 }` · `401` · `403`

## 5. Asynchronous events and integration contracts

### 5.1 Broker topology (RabbitMQ)

| Exchange (type) | Routing keys | Queue (consumer) | DLQ |
|---|---|---|---|
| `wallet.commands` (direct) | `wallet.debit`, `wallet.credit`, `wallet.reverse` | `wallet-service.commands` (Wallet) | `wallet-service.commands.dlq` |
| `wallet.events` (topic) | `wallet.debited`, `wallet.debit.rejected`, `wallet.credited`, `wallet.credit.failed`, `wallet.debit.reversed`, `wallet.balance.changed` | `transfer-service.wallet-events` (Transfer, all but balance), `wallet-service.balance-projection` (Wallet, `wallet.balance.changed`) | `*.dlq` |
| `transfer.events` (topic) | `transfer.completed`, `transfer.rejected`, `transfer.reversed` | `notification-service.transfer-events` (Notification) | `notification-service.transfer-events.dlq` |
| `audit.events` (fanout) | — | `audit-service.records` (Audit) | `audit-service.records.dlq` |

All queues are durable quorum queues. Producers use publisher confirms. Consumers ack manually after committing.

### 5.2 Message envelope

Every message (headers + body) follows:

```json
{
  "messageId": "0b8e…",
  "type": "DebitWallet",
  "version": 1,
  "occurredAt": "2026-10-16T15:04:05.101Z",
  "correlationId": "5f0c…",
  "transferId": "a3f9…",
  "producer": "transfer-service",
  "payload": { }
}
```

### 5.3 Delivery guarantees (all events)

- **Publishing:** transactional outbox in the producer's database; a relay publishes pending rows with publisher confirms, then sets `publishedAt`. The Gateway publishes audit events directly (fire-and-forget with local retry) because it has no database; the Transfer Service also audits every accepted request, so no accepted attempt can be missing.
- **Delivery:** at least once. **Idempotency:** every consumer stores `messageId` in `processed_messages` in the same transaction as its effect; Wallet additionally enforces `UNIQUE(transferId, type)` on ledger entries.
- **Ordering:** per `transferId` the saga sends one command at a time and waits for its reply, so ordering is guaranteed by the protocol. Balance projection uses `version` to discard stale events.
- **Retries:** consumer retries 3 times with exponential backoff (1 s, 5 s, 25 s), then the message goes to the DLQ and an alert is raised. Saga step timeout: 10 s per attempt, 3 attempts, then compensation.

### 5.4 Commands (Transfer → Wallet)

| Name | Producer | Consumer | Exchange / routing key | Payload | Reply |
|---|---|---|---|---|---|
| `DebitWallet` | Transfer | Wallet | `wallet.commands` / `wallet.debit` | `{ transferId, walletId, amount, currency }` | `WalletDebited` or `DebitRejected` |
| `CreditWallet` | Transfer | Wallet | `wallet.commands` / `wallet.credit` | `{ transferId, walletId, amount, currency }` | `WalletCredited` or `CreditFailed` |
| `ReverseDebit` | Transfer | Wallet | `wallet.commands` / `wallet.reverse` | `{ transferId, walletId, amount, currency, reason }` | `DebitReversed` |

### 5.5 Wallet events

| Name | Producer | Consumers | Routing key | Payload |
|---|---|---|---|---|
| `WalletDebited` | Wallet | Transfer, Audit (copy to `audit.events`) | `wallet.debited` | `{ transferId, walletId, amount, balanceAfter, version }` |
| `DebitRejected` | Wallet | Transfer, Audit | `wallet.debit.rejected` | `{ transferId, walletId, reason: "INSUFFICIENT_FUNDS" \| "WALLET_BLOCKED" }` |
| `WalletCredited` | Wallet | Transfer, Audit | `wallet.credited` | `{ transferId, walletId, amount, balanceAfter, version }` |
| `CreditFailed` | Wallet | Transfer, Audit | `wallet.credit.failed` | `{ transferId, walletId, reason: "WALLET_NOT_FOUND" \| "WALLET_BLOCKED" }` |
| `DebitReversed` | Wallet | Transfer, Audit | `wallet.debit.reversed` | `{ transferId, walletId, amount, balanceAfter, version }` |
| `BalanceChanged` | Wallet | Wallet balance projection (Redis) | `wallet.balance.changed` | `{ walletId, userId, available, currency, version, occurredAt }` |

### 5.6 Transfer events

| Name | Producer | Consumers | Routing key | Payload |
|---|---|---|---|---|
| `TransferCompleted` | Transfer | Notification, Audit | `transfer.completed` | `{ transferId, senderUserId, receiverUserId, amount, currency, completedAt }` |
| `TransferRejected` | Transfer | Notification, Audit | `transfer.rejected` | `{ transferId, senderUserId, amount, currency, reason }` |
| `TransferReversed` | Transfer | Notification, Audit | `transfer.reversed` | `{ transferId, senderUserId, amount, currency, reason, reversedAt }` |

### 5.7 Audit events (`audit.events`)

`AttemptRecorded` — producers: Gateway, Transfer, Wallet. Consumer: Audit.

```json
{
  "transferId": "a3f9… | null",
  "userId": "u-123",
  "source": "GATEWAY | TRANSFER | WALLET",
  "action": "TRANSFER_REQUESTED | DEBIT | CREDIT | REVERSAL | TRANSFER_FINISHED",
  "outcome": "ACCEPTED | REJECTED | DUPLICATE_REPLAYED | IN_PROGRESS_CONFLICT | KEY_REUSED | SUCCEEDED | FAILED | COMPENSATED",
  "amount": "150000.00",
  "currency": "COP",
  "reason": "INSUFFICIENT_FUNDS | FINANCIAL_SESSION_INVALID | … | null",
  "idempotencyKey": "4e2b…",
  "occurredAt": "2026-10-16T15:04:05.101Z"
}
```

Audit ignores duplicates by `eventId` (= `messageId`) and appends with hash chaining.

```yaml
    AttemptRecorded:   { payload: { type: object, required: [source, action, outcome, occurredAt], properties: { transferId: {type: string}, userId: {type: string}, source: {type: string}, action: {type: string}, outcome: {type: string}, reason: {type: string}, occurredAt: {type: string, format: date-time} } } }
```

## 6. Requirements and scenarios (WHEN / THEN)

### Feature 1 — Robust authentication and financial session management

- **WHEN** a user logs in with valid credentials from a registered device **THEN** Identity returns a 15-minute access token and a 7-day rotating refresh token bound to that device.
- **WHEN** a login fails 5 times within 15 minutes **THEN** the account is locked for 15 minutes and further logins return `423 ACCOUNT_LOCKED`.
- **WHEN** a client calls `POST /transfers` without `X-Financial-Session`, or with an expired, already used or other-device token **THEN** the Gateway returns `403 FINANCIAL_SESSION_REQUIRED | FINANCIAL_SESSION_INVALID`, nothing reaches the Transfer Service, and an `AttemptRecorded(outcome=REJECTED)` is published.
- **WHEN** a refresh token that was already rotated is reused **THEN** the whole token family is revoked and the user must log in again.
- **WHEN** a user logs out **THEN** the access token `jti` is stored in Redis and any further request with it returns `401 TOKEN_REVOKED`.

### Feature 2 — Balance read optimized for speed and high concurrency

- **WHEN** `GET /wallets/me/balance` is called and `balance:{userId}` exists in Redis **THEN** the response comes from Redis without touching PostgreSQL.
- **WHEN** the cache entry is missing **THEN** Wallet reads PostgreSQL, writes the entry with its `version`, and returns `200`.
- **WHEN** a `BalanceChanged` event with `version` 41 arrives after version 42 was stored **THEN** the projection discards it and the cache keeps version 42.
- **WHEN** a transfer is validated **THEN** the debit uses the PostgreSQL balance (authoritative), never the cached value.

### Feature 3 — P2P transfers protected by strict idempotency at the Gateway

- **WHEN** `POST /transfers` arrives without `Idempotency-Key` **THEN** the Gateway returns `400 IDEMPOTENCY_KEY_REQUIRED`.
- **WHEN** a user taps "Transfer" 10 times in one second with the same key **THEN** exactly one request reaches the Transfer Service, the others receive `409 IDEMPOTENCY_IN_PROGRESS` or the replayed `202`, the sender is debited once, and each duplicate is audited as `DUPLICATE_REPLAYED` or `IN_PROGRESS_CONFLICT`.
- **WHEN** a key already `COMPLETED` is sent with the same body **THEN** the stored response is returned with `Idempotent-Replayed: true` and nothing is executed.
- **WHEN** the same key is sent with a different body **THEN** the Gateway returns `422 IDEMPOTENCY_KEY_REUSED`.
- **WHEN** the Redis check is bypassed or the key expired **THEN** `UNIQUE(sender_user_id, idempotency_key)` in `transfer_db` rejects the duplicate and the existing transfer is returned.

### Feature 4 — Saga with transactional outbox and automatic compensation

- **WHEN** a transfer is accepted **THEN** the `Transfer(PENDING)` row and its `DebitWallet` outbox row are committed in the same transaction and the API returns `202 Accepted`.
- **WHEN** the debit succeeds and the credit succeeds **THEN** the transfer ends `COMPLETED` and `TransferCompleted` is published.
- **WHEN** the sender has insufficient funds **THEN** the conditional debit updates 0 rows, Wallet publishes `DebitRejected`, the transfer ends `REJECTED`, and the balance never goes below zero.
- **WHEN** the network fails after the debit and the credit fails or times out after 3 attempts **THEN** the saga moves to `COMPENSATING`, sends `ReverseDebit`, the sender's balance is restored, and the transfer ends `REVERSED`.
- **WHEN** the Transfer Service crashes after committing but before publishing **THEN** the outbox relay publishes the pending message on restart and the saga continues.
- **WHEN** Wallet receives the same `DebitWallet` twice **THEN** the second delivery is ignored (`processed_messages` and `UNIQUE(transferId, type)`) and the original result is re-emitted.

### Feature 5 — Immutable (append-only) audit of every attempt

- **WHEN** any transfer attempt happens (accepted, rejected, duplicate, failed, compensated) **THEN** an `AttemptRecorded` event is stored in `audit_records` with its hash chained to the previous record.
- **WHEN** someone runs `UPDATE` or `DELETE` on `audit_records` **THEN** the database rejects it (privileges revoked and trigger).
- **WHEN** a record is altered outside the application **THEN** `GET /audit/verify` returns `valid: false` with the first broken `seq`.
- **WHEN** the Audit Service is down **THEN** transfers keep working, audit events wait in `audit-service.records`, and they are stored once the service recovers.
